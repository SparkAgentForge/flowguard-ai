# FlowGuard AI 技术架构

> 文档版本：V0.1  
> 目标：让文本处理、视频推理和业务系统可以并行开发，并通过稳定接口完成集成。

## 1. 架构结论

系统采用“业务审计平台 + 独立 AI 服务”的模块化架构：

- FlowGuard Backend 是唯一业务入口，负责权限、SOP 版本、工单状态和审计记录。
- Document AI 负责把 PDF/DOCX 转成候选 SOP，但无权自动发布。
- DeepStream SOP 负责视频步骤识别，不直接修改工单状态。
- Audit Engine 根据已发布 SOP 和推理结果作出规则判断。
- 前端只通过 FlowGuard Backend 操作，不直接调用 AI 服务。

这样可以替换模型、使用模拟服务、单独部署 GPU 节点，同时保持业务逻辑稳定。

## 2. 总体架构

```text
┌────────────────────── FlowGuard Web ──────────────────────┐
│ SOP 审核 │ 工单中心 │ 异常证据 │ 返工任务 │ 报告归档     │
└──────────────────────────┬─────────────────────────────────┘
                           │ HTTPS / JSON
┌──────────────────────────▼─────────────────────────────────┐
│                    FlowGuard Backend                        │
│  Auth │ SOP Service │ Work Order │ Audit Engine │ Report   │
│              Job Worker │ Notification │ Adapters          │
└───────────────┬──────────────┬──────────────────┬───────────┘
                │              │                  │
        ┌───────▼──────┐ ┌─────▼──────────┐ ┌────▼──────────┐
        │ Document AI  │ │ Inference API  │ │ PostgreSQL    │
        │ PDF/DOCX/LLM │ │ Mock/DeepStream│ │ + Object Store│
        └──────────────┘ └─────┬──────────┘ └───────────────┘
                               │
                     NVIDIA GPU / Linux / Docker
```

## 3. 推荐技术栈

| 层级 | 推荐方案 | 原因 |
| --- | --- | --- |
| 前端 | React + TypeScript | 组件生态成熟，适合审核和工单界面 |
| 后端 | Python + FastAPI | 与文档 AI、DeepStream API 和数据处理技术栈一致 |
| 数据库 | PostgreSQL | 适合状态事务、审计记录和结构化 JSON |
| 文件存储 | MinIO，生产环境可替换为 S3 | 保存原始文档、视频、关键帧和报告 |
| 后台任务 | MVP 使用数据库任务表 + Worker | 降低部署复杂度，后续可替换 Celery/队列 |
| 视频推理 | NVIDIA DeepStream SOP 独立服务 | 使用 DDM/GEBD 分段和 VLM 动作判断 |
| 部署 | Docker Compose | 比赛环境可重复部署，便于 B、C 联调 |

MVP 不引入 Kubernetes 和微服务注册中心。Kafka 仅作为 DeepStream 可选输出，不作为业务主链路依赖。

## 4. 模块边界

### 4.1 FlowGuard Web

- 文档上传和解析进度
- 原文与 SOP 提取结果对照审核
- SOP 版本发布
- 工单列表和详情
- 视频步骤时间线及证据查看
- 异常确认和返工任务操作
- 返工复核和报告下载

前端不得自行计算最终合格状态，所有状态转换由后端完成。

### 4.2 FlowGuard Backend

- 用户和角色鉴权
- SOP、工单、异常、返工和报告 API
- 状态机和事务控制
- AI 服务调用及结果校验
- 审计日志和幂等处理
- 文件上传授权和下载鉴权

### 4.3 Document AI

处理流程：

```text
文件校验
  → 文本提取
  → 扫描件 OCR（需要时）
  → 章节和表格分块
  → LLM 结构化提取
  → JSON Schema 校验
  → 原文出处绑定
  → 生成待审核版本
```

AI 输出只能进入 `AI_EXTRACTED`，不能直接进入 `PUBLISHED`。

### 4.4 Inference Adapter

为业务系统提供统一接口，包含两个实现：

- `MockInferenceAdapter`：读取固定结果，用于 C 独立开发和稳定演示。
- `DeepStreamInferenceAdapter`：调用 B 部署的真实 GPU 推理服务。

通过环境变量选择实现，业务代码不出现 DeepStream 专用判断。

### 4.5 Audit Engine

输入：已发布 SOP、步骤时间线、模型置信度和证据。

输出：

- `PASS`：步骤完整且顺序正确。
- `VIOLATION`：有足够证据证明漏步或乱序。
- `INSUFFICIENT_EVIDENCE`：遮挡、低置信度或关键画面缺失。

Audit Engine 只应用确定性规则。候选原因由单独的分析模块生成，并明确标记为推测。

### 4.6 Workflow 与 Notification

- Workflow 管理异常确认、返工、复核和归档状态。
- Notification 订阅状态变化并发送站内消息。
- 邮件或企业微信使用适配器接入，发送失败不回滚工单状态。

### 4.7 Evidence 与 Report

- 原始文件保存到对象存储。
- 数据库保存文件哈希、路径、类型、大小和关联对象。
- 报告内容由数据库事实生成，不让 LLM 自由编造。
- LLM 只可润色说明文字，关键字段从结构化记录填充。

## 5. 核心数据契约

所有契约使用版本字段。新增字段保持向后兼容，删除或改变含义时升级主版本。

### 5.1 SOP 定义

```json
{
  "schemaVersion": "1.0",
  "sopId": "sop_pump_cover",
  "version": "1.3-r2",
  "status": "PUBLISHED",
  "productCode": "PUMP-A01",
  "steps": [
    {
      "id": "install_seal",
      "sequence": 2,
      "name": "安装绿色密封圈",
      "required": true,
      "preconditions": ["scan_part"],
      "evidenceRequirements": ["密封圈完全进入槽位"],
      "onMissing": "BLOCK",
      "sourceRefs": [
        {"fileId": "file_001", "page": 6, "quote": "安装绿色密封圈"}
      ]
    }
  ]
}
```

### 5.2 推理请求

```json
{
  "requestId": "req_001",
  "workOrderId": "wo_001",
  "sopId": "sop_pump_cover",
  "sopVersion": "1.3-r2",
  "videoUrl": "signed://video/input.mp4",
  "callbackUrl": "https://flowguard/api/v1/inference/callback"
}
```

### 5.3 推理结果

```json
{
  "schemaVersion": "1.0",
  "requestId": "req_001",
  "status": "SUCCEEDED",
  "model": {"name": "cosmos-reason", "version": "prompt-07"},
  "timeline": [
    {
      "stepId": "scan_part",
      "startMs": 3000,
      "endMs": 6500,
      "confidence": 0.96,
      "evidence": [{"type": "frame", "uri": "signed://evidence/001.jpg"}]
    }
  ],
  "observations": [
    {
      "type": "STEP_NOT_OBSERVED",
      "stepId": "install_seal",
      "confidence": 0.93,
      "message": "在预期时间窗口内未观察到该步骤"
    }
  ]
}
```

推理服务只报告观察结果，不直接输出“工单已阻断”或“人员违规”。

### 5.4 审计决定

```json
{
  "decision": "VIOLATION",
  "ruleCode": "REQUIRED_STEP_MISSING",
  "stepId": "install_seal",
  "sopVersion": "1.3-r2",
  "facts": ["在预期时间窗口内未观察到安装密封圈"],
  "evidenceIds": ["evidence_001"],
  "requiresHumanConfirmation": true
}
```

## 6. API 边界

MVP 核心接口：

```text
POST   /api/v1/documents
GET    /api/v1/documents/{id}/parse-status
GET    /api/v1/sops/{id}
PATCH  /api/v1/sops/{id}/draft
POST   /api/v1/sops/{id}/submit-review
POST   /api/v1/sops/{id}/approve
POST   /api/v1/sops/{id}/publish

POST   /api/v1/work-orders
POST   /api/v1/work-orders/{id}/videos
POST   /api/v1/work-orders/{id}/inspect
GET    /api/v1/work-orders/{id}

POST   /api/v1/exceptions/{id}/confirm
POST   /api/v1/exceptions/{id}/reject
POST   /api/v1/exceptions/{id}/rework-task
POST   /api/v1/rework-tasks/{id}/videos
POST   /api/v1/rework-tasks/{id}/review

GET    /api/v1/reports/{workOrderId}
GET    /api/v1/reports/{workOrderId}/pdf
POST   /api/v1/inference/callback
```

所有创建和回调接口接收 `Idempotency-Key`，防止网络重试产生重复记录。

## 7. 数据模型

核心实体：

| 实体 | 关键关系 |
| --- | --- |
| `documents` | 原始操作手册，一个文档可产生多个 SOP 草稿 |
| `sops` / `sop_versions` | SOP 主体及不可变版本 |
| `sop_steps` | 某个 SOP 版本的步骤和规则 |
| `work_orders` | 固定关联一个 SOP 版本 |
| `media_files` | 原视频、返工视频、关键帧和报告文件 |
| `inference_jobs` | 推理请求、进度、模型和提示词版本 |
| `observations` | 模型观察到的原始事实 |
| `audit_decisions` | 规则引擎判断及人工确认结果 |
| `rework_tasks` | 返工内容、负责人和完成状态 |
| `audit_events` | 只追加、不覆盖的审计事件 |
| `notifications` | 通知内容、渠道和发送状态 |
| `reports` | 报告版本、哈希和归档时间 |

已发布 SOP、审计事件和归档报告采用只追加策略，不能原地覆盖。

## 8. 稳定性设计

### 8.1 幂等和重复回调

- `requestId + eventType` 建立唯一约束。
- 重复推理回调返回成功，但不重复创建异常。
- 返工任务创建和通知发送分别记录状态。

### 8.2 超时与重试

- AI 调用使用后台任务，不占用普通 HTTP 请求。
- 文档解析和推理调用设置超时并进行有限次数重试。
- 连续失败后进入 `FAILED`，展示明确原因，允许人工重试。

### 8.3 降级

- DeepStream 不可用：切换 Mock，不影响业务演示。
- LLM 不可用：允许人工创建 SOP 草稿。
- 通知渠道不可用：保留站内任务，不阻塞工单。
- PDF 报告失败：JSON 记录仍可归档，PDF 可重新生成。

### 8.4 数据一致性

- 工单状态变化、审计事件和返工任务在同一数据库事务中写入。
- 文件先上传成功并计算哈希，再创建业务关联。
- 工单始终绑定检测开始时的 SOP 版本，后续发布新版本不影响历史工单。

## 9. 安全与审计

- 使用角色权限限制 SOP 发布、异常确认和最终放行。
- 文件下载使用短期签名地址。
- API 密钥和模型令牌只放在环境变量或密钥服务中。
- 审计事件记录操作者、时间、旧状态、新状态、请求追踪编号和备注。
- 视频、文档和报告设置保存期限；比赛数据不得包含未经授权的个人敏感信息。

## 10. 并行开发方案

### A：数据收集

目录和清单建议：

```text
dataset/
  manifest.json
  normal/
  missing_step/
  out_of_order/
  occluded/
  rework/
  annotations/
```

`manifest.json` 至少记录视频编号、场景、预期步骤、异常类型、训练/测试用途和授权状态。

### B：Prompt 调优与推理

- 以统一推理结果 JSON 为唯一交付接口。
- 每次调整记录 `promptVersion`、测试集和指标。
- 保留正常、漏步、遮挡三类固定回归样例。
- 与 C 共同维护健康检查、容器启动和部署说明。

### C：前后端

- 第一周直接使用 MockInferenceAdapter。
- 先完成 SOP 审核、工单状态机和三段演示闭环。
- 接入真实 DeepStream 时只更换 Adapter 配置。
- 负责统一 Docker Compose、数据库迁移和部署入口。

### D：文本处理与项目收尾

- 负责 SOP 提取 Prompt、结构校验和原文出处质量。
- 向 C 提供三份成功样例和至少一份失败/模糊样例。
- A 完成数据后，共同形成客户痛点、成本收益和演示案例。
- 维护商业材料、最终报告和答辩口径。

## 11. 联调顺序

1. C 发布数据契约和 Mock 结果。
2. D 交付 SOP 解析样例，C 完成审核页。
3. A 交付第一批带标注视频，B 开始调优。
4. C 使用 Mock 走通异常、返工和归档闭环。
5. B 输出真实推理接口，C 替换 Adapter 联调。
6. B、C 在目标部署环境完成一键启动和健康检查。
7. A、D 使用真实效果完善商业数据和演示材料。
8. 全组冻结演示数据、Prompt、SOP 和镜像版本，进行回归演练。

## 12. 部署拓扑

```text
普通服务器 / 开发机
  - flowguard-web
  - flowguard-api
  - flowguard-worker
  - postgres
  - minio

NVIDIA GPU Linux 节点
  - deepstream-sop
  - DDM / Triton
  - VLM / vLLM
```

两个节点通过受控 HTTP 接口通信。比赛只有一台 GPU 服务器时，也可以使用同一台 Linux 主机运行全部容器，但仍保持逻辑分离。

## 13. 发布门禁

最终演示版本必须满足：

- 数据库可从空环境自动初始化。
- Mock 模式和真实推理模式均能启动。
- SOP 未批准时不能创建正式检测任务。
- 重复回调不会产生重复异常。
- 漏装流程能完成阻断、确认、返工、复核和归档。
- 遮挡流程不会被自动判为人员违规。
- 报告中的 SOP、模型、Prompt、视频和人工决定均可追溯版本。
- B、C 使用同一份部署说明在干净环境完成部署。
